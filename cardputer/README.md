# Cardputer (M5Stack Cardputer ADV)

Stamp-S3A (ESP32-S3FN8, 8 MB flash, **no PSRAM**, ~95 KB internal free at runtime).
A keyboard-first handset: a little launcher OS (`shell.c`) with apps, the first
of which is the Walkie-Talkie. Speaks the Satellite Protocol.

Build/flash like the other boards (`bash build.sh cardputer`), but flash the
**app only at 0x10000** to keep NVS/WiFi provisioning:

```
python -m esptool --chip esp32s3 -p /dev/ttyACM0 -b 460800 \
  --before default_reset --after hard_reset write_flash \
  0x10000 build/sapphire-cardputer.bin
```

## The screen — hard-won, read before you touch `screen.c`

ST7789V2 240×135. The glass is wired **portrait** (135 cols × 240 rows) but held
**landscape**, and three separate bugs made it look broken for a long time. All
three are fixed; here is what bit us so it doesn't bite again.

1. **No framebuffer — strip renderer.** There is no PSRAM, and once WiFi + the
   HTTP server + voice TLS are up the internal heap is fragmented (largest free
   block ~50 KB). A full 240×135×2 = 63 KB framebuffer **cannot be allocated**
   contiguously, so any paint that mallocs one silently fails ("no RAM to
   paint") and the screen freezes on its last good frame. We render in
   native-row **strips** straight into one ~6.5 KB static buffer: `render_scene`
   walks the panel a strip at a time and re-runs the draw for each; `px()` maps
   each landscape pixel into the current strip (transpose + flip + byte-swap
   inline) and drops the rest. Screen RAM is fixed and a paint can never run out.
   Do **not** reintroduce a full framebuffer.

2. **esp_lcd `draw_bitmap` is asynchronous — wait for the DMA.** It queues the
   SPI/DMA transfer and returns. We reuse one `line` buffer for every strip, so
   refilling it before the previous strip's transfer finished made the DMA read
   a half-rewritten buffer → **letters shredded into vertical bands** (this was
   the "jank the whole time"). Fix: register `on_color_trans_done` and block on
   a semaphore after every `draw_bitmap` (`blit()`), so the buffer is only
   touched once the transfer is done. Any renderer that reuses a shared buffer
   must do this.

3. **Geometry: flip 0/1, gap 52/40.** No hardware swap/mirror (it fought the
   panel offset); rotation is done in software by `px()`. The gap is the glass's
   offset in GRAM: **gap_x = 52** (CASET / landscape-Y) and **gap_y = 40**
   (RASET / landscape-X) — the standard Cardputer window. We shipped 52/52 for a
   while and it pushed everything right (left margin, right edge clipped). If the
   image is off, it's almost always the gap.

4. **The font must be complete.** `font8x8.h` is generated by
   `scratchpad/make_font.py`. An early version only generated the letters the
   original hardcoded words used, so new labels (BACKUP, TERMINAL…) hit blank
   glyphs and dropped letters (`BACKUP` → `A K P`). The generator now fills all
   of A–Z, a–z, 0–9 and common punctuation. Add glyphs there and regenerate,
   never by hand-editing the header.

### Calibrating on glass (no reflash)

The console tunes geometry live, which is how 52/40 was found. Point a camera at
the panel (we used an OBS virtual cam on `/dev/video2`, captured with ffmpeg):

- `screen cal`   — white-on-black: edge border + centre line + full alphabet.
  Best single view for edges / centering / letters on a tiny webcam.
- `screen ruler` — gray fill + solid edge bands (white=L, green=R, cyan=T,
  yellow=B) + centre dashes. Best for "does every pixel paint, flush to edge".
- `screen test`  — border + corner colour markers (which corner is which).
- `screen cfg <flipx> <flipy> <gapx> <gapy>` — re-apply and redraw the ruler.
  When you find good values, bake them into the `gap_x/gap_y` defaults.

Note: a 1–3 px line at the extreme edge can look *dashed* on the webcam — that's
sensor aliasing, not a render bug. The 8 px ruler bands are the honest edge test.

## Keyboard (TCA8418)

I2C keypad @0x34 (SDA8/SCL9). Raw key# = row*10 + col + 1. Nav keys as mapped on
metal: **UP=57, DOWN=58, SELECT=67, BACK=65**, and **Ctrl=4** is push-to-talk in
the Walkie app. Enter is off-matrix and does not register. `shell.c` is the one
reader of the FIFO. `board_kbd_hold()`/`board_kbd_busy()` let the console stand
the shell down during a key dump, so calibration doesn't race the FIFO.

## Storage (microSD)

`storage.c` mounts the TF card at **/sdcard** (FAT32) over its **own SPI bus
(SPI2** — the screen owns SPI3): SCK=40, MISO=39, MOSI=14, CS=12 (the standard
Cardputer SD pinout, `board.h BOARD_SD_*`). Verified on a 32 GB card (SD32G,
~29 GB free).

**Mounted on demand, not at boot.** FATFS + the SPI/SD driver cost ~37 KB, and
this board has no PSRAM — the Walkie-Talkie (the primary app) needs that RAM and
never touches the card, so holding the mount through every walkie session is the
wrong trade. `storage_start()` mounts, `storage_stop()` unmounts and frees the
bus. Console **`sd`** mounts on demand and reports card/room; the disk-using apps
(IR / Backup / Terminal) mount on enter and free on exit. Idle and during the
walkie, the card is unmounted and the RAM is the walkie's. Apps keep their data
in plain files under `/sdcard/<app>/...`; the sealed-backup protocol (cf. the
T-Dongle's `storage.c`) will come with the Backup app, not here.

## The voice pipeline — why TTS playback is smooth (hard-won 2026-10-23)

Sapphire sends her reply one sentence per `POST /audio/speak`, waiting for each
to be answered before the next. Getting that gapless on a no-PSRAM board over a
congested 2.4 GHz link took a stack of fixes — the diagnosis mattered more than
any single change, so a `diag` log line per sentence (gap / recv-time / bytes /
whether the ring ran dry) is still in `on_speak`; **remove it once the voice is
settled.** The chain, in order of what each solved:

1. **Answer when taken in, not when played.** `on_speak` answers 200 as soon as
   the sentence is in the ring, so Sapphire sends the next while this one still
   sounds and it queues behind it — no hole at the joint (the protocol's
   "0.7.7+ answer when taken in"). `priming` rebuilds the start cushion only when
   the ring has caught up, so it never pauses mid-reply; a ~5 ms fade in/out at
   the edges of sound (`FADE`) turns any residual skip into a soft dip, not a
   hard cut. `play_task` is pinned to core 1 (off WiFi/httpd).
2. **The real bottleneck was WiFi throughput, not delivery.** The diag proved
   it: the gap between sentences is ~150 ms (delivery is fine), but 16 kHz PCM
   needs 256 kbps and a congested link (Zigbee + ESP32 bleed + a wall) dips
   below that. Don't rearchitect delivery; **send fewer bytes.**
3. **ADPCM codec (the fix).** `/health` advertises `plays.codec: "ima_adpcm"`;
   Sapphire encodes IMA ADPCM WAV (`core/devices/audio_codecs.py`, a DRY codec
   registry — add Opus = one entry), 4:1, ~64 kbps, full 16 kHz quality. The
   board decodes it (`ima_decode_block`). 8 kHz PCM also works but sounds
   telephone-muffled; ADPCM keeps the band.
4. **Store the COMPRESSED audio in the ring, decode at playout.** The ring holds
   framed ADPCM (`[type][len16][payload]`), not decoded PCM, so the same 48 KB is
   **~6 s of cushion** instead of 1.5 s — enough to coast over a 1-2 s WiFi dip
   or a generation gap. Result: **0 skips** even with the link at 56 kbps. This
   is the capstone; it needs no extra RAM (the 48 KB ring is the ceiling — see
   below).

**The 48 KB ring is a hard ceiling.** A 96 KB ring dropped the largest free
block to ~31 KB and starved the voice path (PTT stuck on LISTEN, events dropped
to NO LINK): no PSRAM, and during a PTT turn the ring + two HTTP clients (events
long-poll + voice POST) + WiFi all draw from one internal heap. Do not grow it —
storing compressed is what buys the cushion instead.

## Status indicator

No LED on this board, so the Walkie page shows a **corner square** (`scene_page`)
in the state colour plus the status word. The brain's state from the events
stream (`link.c take_line`: thinking/tool → think, speaking, idle, error →
nolink) drives it via `light_cue` → `shell_cue` (painted only while the Walkie
app is open). *Known cosmetic:* SPEAKING is still driven by `on_speak` receive
timing, so it can read READY during the tail of a reply; audio is unaffected.

## IR blaster (2026-10-23)

Onboard IR **emitter on GPIO44**, driven by the RMT peripheral at a 38 kHz
carrier (`ir.c`). Phase 1 sends standard 8-bit **NEC** frames (`ir_send_nec`);
raw/learned codes and other protocols slot in later. **No onboard receiver** —
learn mode needs an external IR unit (the ~$5 M5 Mini IR Unit, or a 3-pin RX on
a free GPIO like GPIO1), confirmed against the spec.

- Console: `ir <addr_hex> <cmd_hex>` (LG TV power = `ir 04 08`, proven on glass).
- Server: `POST /ir/blast?addr=04&cmd=08`; `/health` advertises `ir` in `has`.
  `ir_send_nec(uint16_t addr, uint8_t cmd)` does standard NEC when addr ≤ 0xFF
  (LG, addr 0x04) and **NEC-extended** when addr > 0xFF (a 16-bit address sent
  as-is, e.g. a TCL Android TV at 0x57E3).
- Sapphire side: `ir` capability in `core/devices/drivers/satellite.py` (describe
  + run `blast`), the **IR library** `core/ir/library.py` (appliances → named
  commands → codes, name resolution, built-in brand import), the route
  `core/routes/ir.py` (`/api/ir/*`), and the **UI** — a pane in Device Manager
  (Devices > IR, `settings-tabs/ir.js`): bordered appliance cards, add/import/
  edit/delete, per-command Test, add-command tucked behind a button, a kebab
  (Import/Export/Remove), + Add appliance as a modal. Proven end to end:
  `device_action(cardputer, ir, "blast", "tv power")` runs the LG, by voice too.
- **Both TVs work by IR, no WiFi.** LG is standard NEC (addr 0x04); the **TCL
  Roku** turned out to be **NEC-extended, address 0xC7EA** (the Flipper-IRDB
  `TCL_ROKU_US` set — power 0x17, plus home/back/arrows/select) — NOT the
  proprietary wall first assumed, just the wrong codes. The `TCL Roku TV` and
  `TCL TV (Android)`, 0x57E3) brands are both in the table. Lesson: check the IR
  databases (Flipper-IRDB, IRDB) before declaring a device uncrackable.
- Still ahead for IR: **raw-IR blast** on the board (arbitrary timings, for codes
  that are not NEC at all) + a `tools/ir_learn.py` that drives a USB-UIRT / M5 IR
  Unit to capture one (keep the USB dependency in a tool, not the web backend);
  TCL Roku volume (not in that .ir file); favorites→SD sync + a standalone
  on-board IR app; more brands / an online-DB import.
